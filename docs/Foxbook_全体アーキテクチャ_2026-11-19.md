# Foxbook 全体アーキテクチャ

- 作成日: 2026-11-19
- 基礎文書: [Foxbook 全体アーキテクチャ 2026-11-16](Foxbook_全体アーキテクチャ_2026-11-16.md)
- 状態: 現状と設計検討案。共通音声アシスタントは未実装
- 対象: Firefoxキオスク環境 Foxbook、関連拡張、Native Messaging Host、ローカルサービス

本書は2026-11-16版を基に、共有音声基盤とTHE SESSION TOOLSの現在の連携、および複数アプリを対象とする音声アシスタントの議論を反映した新版である。現行の契約・検証状況は[横断管理台帳](cross-repo-ledger.md)と[インターフェース索引](interfaces/index.md)を正本とし、本書の構想だけで既存契約を変更しない。

## 1. 目的と設計原則

FoxbookはLinux上のFirefoxを中心に、タッチ操作・音声入力・ローカルファイル操作・開発支援・楽譜閲覧を統合する環境である。Firefox拡張は利用目的に固有のUIと機能を担当し、OS資源へのアクセスは用途を限定したNative Messaging Hostを経由する。共有ハードウェアや高コストな処理は、必要に応じてローカルサービスへ集約する。

1. WebページからOS操作へ直接到達できる経路を設けない。
2. 拡張とNative Hostは許可された操作のみを公開し、接続先や操作を明示的に制限する。
3. 共有音声基盤、音声アシスタント、各アプリの機能を責務として分離する。アシスタントを使わない利用者は共有音声基盤を直接利用できるようにする。
4. 最小権限、明示的な利用開始、失敗時の安全な停止を優先する。
5. 既存の拡張間契約を維持し、変更が必要な場合は契約と移行方法を明確にする。

## 2. 現在の構成

以下は実装済みの接続を簡略化した概念図である。リポジトリはソースコードの所有単位であり、実行プロセスの数を表さない。

```text
Firefox
├─ Fox Voice Editor（fox-voice-editor）
│    ├─ fox_voice_editor Host → 履歴・定型文などの編集固有データ
│    └─ foxbook_speech Host ─────────────────────────────┐
│                                                        │
└─ THE SESSION TOOLS                                    │
     ├─ 待機・録音の指示、認識テキストのコマンド解釈       │
     └─ foxbook_speech Host ─────────────────────────────┤
                                                         ↓
foxbook-speech service（foxbook-speech）
  ├─ 録音、認識エンジン・モデル、マイク使用の管理
  ├─ Wake Word検出と検出イベントの通知
  └─ チューナー入力・ピッチ解析などの共有音声処理
```

各拡張はNative Messaging接続ごとに起動する `foxbook_speech` Hostを通じ、Unix domain socketで共有serviceに接続する。Hostは中継を担当し、マイクや認識エンジンの共有状態はserviceが管理する。Fox Voice Editorの編集固有データは別の `fox_voice_editor` Hostが扱う。

THE SESSION TOOLSの通常音声操作では、拡張がWake Word待機を要求し、serviceが検出すると通知する。拡張は録音開始・停止を指示し、serviceが音声を文字に変換して返す。現状の**発話テキストのコマンド解釈と操作実行はTHE SESSION TOOLS側**である。詳細は[IF-TST-SP-001](interfaces/the-session-tools--foxbook-speech.md)を参照する。

共通音声serviceとVoice Editorの二Host接続は実装済みである。実機確認の範囲と保留事項は[検証マトリクス](operations/verification-matrix.md)を参照する。通常Wake Word待機は録音・チューナーと共通のleaseにまだ含まれておらず、マイクの完全な排他を保証するものではない。

## 3. リポジトリと現行コンポーネントの責務

| 所有先・構成要素 | 現在の責務 |
| --- | --- |
| `fox-voice-editor` | 録音UI、認識結果の編集、履歴・定型文、Focodex/OSK連携と、編集データ用Native Host。音声認識には共通音声Hostを利用する。 |
| `foxbook-speech` | 共通音声Native Host、共有service、Wake Word・録音・認識・モデル管理、音声API、導入手順と試験。 |
| `THE SESSION TOOLS` | メトロノーム・チューナーとそのUI。現在はWake Word待機と録音を指示し、返されたテキストを自分で解釈する。 |
| `foxbook` | 横断設計、契約索引、運用と検証の記録。 |

Focodex、FX-OSK、LATO、Setoli、Foxbook Control、Split Viewなどはそれぞれの責務を維持する。共通音声Hostの存在は、端末制御や編集データのHostまで統合することを意味しない。

## 4. 共通音声アシスタントの構想（未実装）

複数アプリを音声操作する場合、アプリごとにWake Word待機、録音制御、発話の解釈、マイク競合への対応を重複させず、共通の管理層で受け持つ構成を検討する。以下は設計上の責務であり、リポジトリや実行プロセスの配置を確定するものではない。

```text
利用者の発話
    ↓
共有音声基盤：Wake Word検出 → 録音 → 音声認識 → テキスト
    ↓
音声アシスタント／管理層：発話を解釈 → 対象候補を決定
    ├─ 一意：対象アプリの操作APIへ送信
    └─ 複数：共通UIに候補を表示 → 音声で追加選択
    ↓
対象アプリ：操作と値を検証 → 実行 → 成功／失敗を返す

Fox Voice Editor ──→ 共有音声基盤を直接利用（従来どおり）
```

| 責務 | 担当すること | 担当しないこと |
| --- | --- | --- |
| 共有音声基盤 | Wake Word、録音、認識、マイク管理、音声処理の状態・結果通知。 | アプリ名や「テンポを上げる」などのアプリ固有の意味の解釈。 |
| 音声アシスタント／管理層 | 音声操作の制御、コマンド解釈、候補決定、確認・配送、共通UIへの状態通知。 | 対象アプリの内部状態の直接操作。音声基盤の利用にアシスタントを必須化すること。 |
| 各アプリ | 自分が提供する操作とコマンド定義、引数・操作状態の検証、実行結果の返却。 | 共通アシスタントを使う場合、複数アプリ横断の候補選択や共通語彙判定。 |
| 共通音声UI | Wake Word待機、認識中、サービスエラー等を常時表示。複数候補の選択肢を表示。 | 表示場所やウィンドウ構成は未決定。 |

Fox Voice Editorのような音声を文字にする用途は、音声アシスタントやそのUIを経由せずに共有基盤を利用できることを維持する。アシスタントの音声入力にfoxbook-speechを使う構成は候補だが、将来の別の認識手段を不必要に排除しない。

## 5. コマンド定義と解釈の構想

各拡張が、自分の操作に対応するコマンド定義をJSONとして配置する方針である。定義には操作の識別子、受け付ける発話表現やアプリ名・別名、必要な引数などを持たせることを想定する。正確な形式、版管理、検証方法、管理層による取得手段は未決定である。ファイルを拡張内に配置することと、外部の管理層から直接読めることは同義ではない。

発話の解釈は、たとえば「テンポ」「少し」「上げて」を対象・変更量・操作として扱い、「を」「ほしい」「ください」などの許容表現を組み合わせる小さな文法を検討する。「テンポを少し上げてほしい」はTHE SESSION TOOLSのテンポ増加へ対応付ける想定である。

語尾の無条件な切り捨てや単純な部分一致は採用前に検証する。「上げてほしくない」のような否定、複数操作や曖昧な表現を誤って実行しないことを重視する。未知・矛盾・曖昧な入力は操作せず、必要な説明や言い直しを促す。構文・語彙・否定の具体的な範囲は未決定である。

管理層の解釈結果は、アプリの限定された操作APIへ構造化した操作と引数として渡す。各アプリは管理層を信頼する場合も、操作の許可、引数の範囲、実行可能な状態を自分で検証する。APIの名前やプロトコルは今後定める。

## 6. 対象アプリの決定と共通UI

現在の検討方針は次のとおりである。

1. 発話にアプリ名・別名があれば、そのアプリに対して操作を解釈する。指定先が存在しない、または操作に対応しない場合は、別アプリへ勝手に振り替えない。
2. アプリ名がない場合、利用可能な拡張のコマンド定義を照合する。候補が一つなら、その拡張へ送る。操作先の確認表示は挟まない。
3. 複数の拡張が該当する場合は、共通UIに選択肢を表示し、音声による追加指示を待つ。
4. 候補がない場合、または「少し上げて」のように操作内容自体が特定できない場合は実行せず、理由や言い直しを案内する。

例として、「テンポを少し上げて」が一つの拡張にしか該当しなければ、そのまま送る。「再生して」が複数の拡張に該当すれば選択を求める。「セッションツールで再生して」は明示指定として扱う。

音声認識UIのための常時表示領域を設け、Wake Word待機中・認識中・サービスエラー等を示す方針である。候補を尋ねる際の音声読み上げ・通知音、表示位置、操作方法は未決定。候補選択中のキャンセル、失効時間、候補外発話、対象アプリの終了時の扱いも決める必要がある。操作の実行直前には対象が利用可能か再確認する案とする。

## 7. 管理層の配置と通信（未決定）

管理層は `foxbook-speech` 内の独立した構成要素として置き、音声基盤とアシスタントを明確に分ける。Voice Editorが基盤だけを利用できる境界を保つ。管理層の最終的な実行プロセスと通信方式は未決定である。

共通UIはWebExtensionsのContent Scriptで対象ページ内に最前面表示し、ドラッグで移動できる構成とする。Firefoxの内部画面・エラー画面・他拡張の画面など注入できないページでは表示されないことを前提に、管理層の動作をUIの存在に依存させない。ページ固有の前面表示やDOM操作によっても重なり順が保証できない場合がある。初期の状態表示は文字とする。`foxbook-speech/assistant-ui/`に表示試作を追加したが、実音声サービス接続や表示不可ページでの音声動作は未実装・未検証である。

管理層が各拡張のJSONを取得する方法、拡張の発見と登録、操作APIの通信経路、アクセス許可、再接続と版互換性は未設計である。各拡張が自分の定義をAPI経由で公開する方法は候補の一つだが、Firefoxの権限や実際の構成を検証してから決定する。

## 8. マイク・性能・セキュリティ

- 共有音声serviceの録音・チューナー要求は共通leaseを使用する。通常Wake Word待機のlease統合と、複数利用者間の完全な排他は引き続き検討・検証が必要である。
- 移行時はTHE SESSION TOOLSと管理層が同時にWake Word待機を開始しないよう、所有者の切り替えと停止・切断時の回収を設計する。
- 音声認識用Native Hostの許可済み拡張ID、入力検証、ローカルIPCの権限を維持する。アプリ操作APIも呼出元と操作範囲を限定し、Webページから任意のOS操作やアプリ操作へ到達できる経路を設けない。
- 録音データは原則一時保存し、停止・取消・切断・異常時の回収を維持する。音声や認識全文をログに不用意に残さない。
- Surface Pro 4を含む対象端末で、モデル常駐・アイドル解放・初回起動時間・メモリ使用量・マイク補正を実測する。

## 9. 既存機能との互換性と段階的検討

Fox Voice Editorの音声API、編集用Host、履歴・定型文、Focodex/OSK連携を維持する。共通アシスタントの追加により、既存の直接録音・文字起こしを使えなくしない。THE SESSION TOOLSの現行音声操作・チューナー・オフライン運用も、移行方法と回帰確認を用意するまでは現行のままとする。

想定する検討順序は次のとおり。実装やリポジトリ変更を決定したものではない。

1. 共通UIの常時表示場所と、待機・エラー・複数候補の状態を整理する。
2. 各拡張の定義取得、限定された操作API、呼出元の許可と版管理を設計する。
3. 発話パターン、否定・曖昧性の扱い、複数候補選択とキャンセル・失効を定義する。
4. THE SESSION TOOLSを最初の対象候補として、定義取得から操作結果返却までを検証する。既存の直接音声操作からの移行とWake Word／マイク所有権を検討する。
5. Voice Editorの既存録音、マイク競合、切断・再接続、オンライン／オフライン、複数拡張、Surfaceでの動作を回帰確認する。

## 11. 設計方針の要約

現在の共有音声基盤は `foxbook-speech` が担当し、THE SESSION TOOLSが自分の音声コマンドを解釈している。将来の共通音声アシスタントでは、各拡張のJSON定義を横断して照合し、一意なら実行、複数候補なら共通UIと追加音声指示で選択する方向を検討する。発話内でアプリを明示する方法も扱う。

管理層はfoxbook-speech内に独立配置し、音声基盤とアシスタントは責務を分け、Voice Editorによる基盤の直接利用を維持する。UIはContent Script方式とし、管理層の実行形態・通信・音声接続の方式は未決定である。
