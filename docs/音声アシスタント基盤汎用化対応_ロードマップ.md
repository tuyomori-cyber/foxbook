# 音声アシスタント基盤汎用化対応ロードマップ

- 作成日: 2026-11-19
- 状態: 第1段階の表示試作と第2段階の拡張間通信試作に着手。第3〜6段階は未着手
- 対象: 音声アシスタント管理層、共通UI、各アプリの音声操作API、共有音声基盤
- 基礎文書: [Foxbook 全体アーキテクチャ 2026-11-19](Foxbook_全体アーキテクチャ_2026-11-19.md)

## 目的と前提

複数のアプリを共通の音声アシスタントから操作できるようにし、Wake Word待機、発話の解釈、操作先の選択と配送をアプリごとに重複させない。各アプリは操作APIとJSON形式のコマンド定義を持ち、自分の状態・引数・操作を検証する。

共通UIにはWake Word待機、認識中、サービスエラー等を常時表示する。アプリ名を含む発話は指定先に対して解釈し、指定がない場合は定義を横断して照合する。一つの拡張だけが該当すれば実行し、複数候補なら表示して音声の追加指示を待つ。該当なし、否定、操作自体が不明な場合は実行しない。

現状、Wake Word検出・録音・認識は `foxbook-speech` が行い、THE SESSION TOOLSが待機・録音を指示し、認識結果を自分で解釈する。録音とチューナーは共通leaseを用いるが、通常Wake Word待機はまだそのleaseに含まれない。現行契約は[IF-TST-SP-001](interfaces/the-session-tools--foxbook-speech.md)を参照する。

音声を伴わない操作配送を先に確認し、続いて音声・マイク・チューナーを移行する。管理層は `foxbook-speech` 内の独立した構成要素とし、音声基盤とアシスタントの責務を分離する。Fox Voice Editorが音声基盤を直接利用できる経路を維持する。管理層の実行形態・通信方式は未決定。本書は現行の音声契約の変更を意味しない。

## Foxbookの信頼境界

ネイティブアプリについては、同一Linuxユーザー内のプロセスを基本的に信頼する。アプリIDは識別・登録・リソース管理に使用し、悪意ある同一ユーザープロセスからの詐称防止は保証しない。

Firefox拡張については、同一ユーザー内であっても自動的には信頼しない。Firefoxが提供する拡張IDを基準に、明示的に許可された拡張のみが対象機能を利用できる。

音声基盤の利用許可と、音声アシスタントの操作対象としての許可は独立して管理する。

Native Messaging HostはFirefoxとネイティブ環境の信頼境界を担当する。拡張から自己申告されたIDは認証情報として扱わない。

音声基盤では接続単位のセッションを管理し、録音の所有権、マイクの排他、接続終了時の解放、認識結果の返却先を制御する。

この節は設計方針であり、ネイティブアプリの登録方式や両許可の独立管理が実装済みであることを意味しない。現行HostはFirefoxの起動引数の拡張IDを許可リストと照合する。一方、serviceの同一ユーザー用Unix socketに直接接続できるプロセスは内部の接続開始メッセージでIDを申告できるため、同一ユーザーの悪意あるネイティブプロセスによる詐称は防がない。

## 登録の設計方針

登録は次の二種類に分け、許可を独立して管理する。

- **foxbook-speech利用登録:** 録音・音声認識などの基盤機能を直接利用するアプリを対象とし、接続元の種類、アプリID、許可する機能などを管理する。
- **音声アシスタント操作対象登録:** 音声コマンドで操作されるアプリを対象とし、接続先の種類とアプリID、コマンド定義の取得方法、APIバージョンなどを管理する。Firefox拡張では拡張IDも登録する。実験中の`getCommands`を発展させる。将来のネイティブアプリの接続方式は未決定。

初期段階では導入・管理時に対象を明示的に設定し、アプリの自己申告だけで自動登録しない。許可は種類ごとに個別に取り消せる方針とする。設定の保存形式、管理者・利用者向けの操作方法、取り消し時の既存接続の扱いは未決定。

現在動作しているfoxbook-speechの接続・認証部分の大幅な作り直しは避け、既存の許可リストを出発点として登録情報と管理機能を段階的に追加する。Fox Voice Editorは音声基盤を直接利用し、THE SESSION TOOLSは将来、登録されたコマンドによる操作対象となる想定。現行のTHE SESSION TOOLSは音声基盤も直接利用しており、移行が完了するまで既存経路を維持する。

## 第2段階：各拡張の操作APIとJSON定義

**内容**

- [x] [独立した2つの試作拡張](../../foxbook-speech/assistant-ui/exchange-probe/README.md)でJSON定義の取得と模擬操作の応答を利用者が確認した。実アプリの操作APIや正式契約は未変更。
- [x] THE SESSION TOOLSの[実験API](interfaces/assistant--the-session-tools.md)で、利用者がFirefoxからBPM +5を確認した。ドメインを開いていない場合は失敗したと報告。
- [x] 利用者が対象タブを非アクティブにした場合の `TARGET_INACTIVE` 表示と、対象拡張を無効化した場合の操作ボタン無効化・接続エラー表示を確認した。端末・Firefoxバージョンと非アクティブ時のBPM値は未記録。正式な管理拡張IDは未決定。
- [ ] 対象拡張の発見・登録、JSON定義の取得、通信と接続切断時の扱いを設計し、Firefoxで実現性を確認する。試作では固定IDを選択して定義取得し、操作中の二重送信を防止、通信失敗は結果不明と表示する（自動試験済み）。試作に5秒の期限と結果不明時の操作無効化を追加し、利用者がダミー対象の正常・遅延・無応答の5条件とポップアップ終了後の遅延実行をFirefoxで確認した。端末・Firefoxバージョンは未記録。[登録と配送の検討](decisions/音声操作対象の登録と配送_検討.md)を参照。動的登録・正式な期限は未決定。
- [ ] 対象の「接続可能」（定義取得などへの応答）と「操作可能」（対象の状態・権限・引数に応じた個別操作の可否）を分ける。接続可能でも実行時に対象側で状態を再検証し、操作できない理由を返す。事前判定は実行成功を保証しない。
- [ ] 操作を要求する `execute` と既存要求を照会する `getRequestStatus` を別APIとして設計する。各要求に一意なIDを付け、同じID・同じ内容の重複を対象側で排除し、同じID・異なる内容は拒否する。照会は操作を実行しない。対象の応答が得られない場合は結果不明とし、自動再実行しない。
- [ ] 管理側の要求状態はポップアップではなくbackgroundで管理し、ポップアップの開閉後も状態を参照できるようにする。backgroundの停止・再起動に備えた保存と復旧の範囲は設計・試験する。常駐や永続化を前提としない。
- [ ] 対象側の重複排除記録とアプリ状態の更新順序・保存・中断後の復旧を契約に明記する。記録と操作の整合性を保証できない中断区間、記録失効・再起動後の状態を定め、判別不能時は結果不明として自動再実行しない。一度だけの実行を無条件に保証しない。
- [ ] コマンド識別子、アプリ名・別名、引数、発話表現、版管理、成功・失敗の形式を定義する。
- [ ] 呼出元の許可、入力検証、範囲外・不正な操作の拒否を設計する。任意のOS操作や任意コマンド実行は公開しない。
- [ ] 最初の対象候補としてTHE SESSION TOOLSの再生・停止、テンポ、音量、分割、チューナー起動を整理する。最初の接続検証は一操作に絞る。

**第3段階へ進む条件:** THE SESSION TOOLSの一操作について、管理層からの通信、要求IDによる重複排除、独立した状態照会が成立し、成功・失敗・結果不明と中断時の扱いを契約化して検証する。接続可能と操作可能を区別し、未許可の呼出元・不正な引数を拒否する。必要な自動試験とFirefox実機確認を記録する。汎用登録や全操作への対応など残りの基盤整備の完了は待たず、第3段階へ進める。

**完了条件:** 上記の一操作の条件を満たし、残る登録・定義・操作の拡張や正式運用に必要な未完了事項を明確にする。

## 第3段階：コマンド解釈と対象選択

**内容**

- [ ] 音声入力とは切り離し、文字列から各拡張のJSON定義を照合する判定処理を検討する。
- [ ] アプリ名の明示指定、一意候補、複数候補、候補なしを扱う。明示した拡張に操作がない場合は他の拡張へ振り替えない。
- [ ] 「テンポを少し上げてほしい」等の対象・変更量・操作・助詞・語尾を組み合わせて解釈する。許容範囲は定義と試験で明確にする。
- [ ] 否定、矛盾、複数操作、不完全な発話、未知の語尾を誤って実行しない。曖昧な場合は言い直しを求める。
- [ ] 選択待ちのキャンセル、失効時間、候補外の発話、選択中の対象終了と再確認を定義する。

**完了条件:** 文字列による試験で、一意候補、明示指定、複数候補、候補なし、否定、曖昧な入力を区別できる。テスト用の別アプリ定義で「再生して」が重複する場合を含める。

**内容**

- [ ] 管理層を音声入力に接続し、Wake Word待機、録音、認識結果、エラーを扱う。初期の音声基盤として `foxbook-speech` の利用を検討する。
- [ ] 共通UIに待機・認識・エラーを表示する。複数候補では選択肢を表示し、追加の音声指示を受け付ける。
- [ ] 管理層の試験中は、THE SESSION TOOLSの既存Wake Word待機と同時に有効化しない。既存方式へ戻す切替方法を用意する。
- [ ] 音声読み上げ・通知音の要否を検討する。チューナーやVoice Editorとのマイク競合については、未検証のまま一般利用に移さない。

**完了条件:** 「みらい、テンポを少し上げて」の認識から一意の対象への操作完了まで通る。複数候補の追加選択、認識失敗・service停止時の非実行、既存方式への復帰を確認する。

## 第5段階：マイクとチューナーの所有権の移行

**内容**

- [ ] 管理層とTHE SESSION TOOLSのどちらがチューナー用接続・所有権を持つかを決める。現行serviceは所有sessionと`tunerId`を検証する。
- [ ] 管理層のWake Word待機を停止し、マイク解放を確認してからチューナーを開始する引継ぎを設計する。
- [ ] チューナー中の「みらい」による終了、停止通知、通常待機への復帰を扱う。
- [ ] Voice Editor録音、通常Wake Word、チューナー間の競合・排他・BUSY・復帰条件を定める。通常Wake Word待機のlease統合を検討する。
- [ ] タブ終了、Host／service切断、開始・停止応答の遅延や競合での回収と、二重待機を防ぐ切替を実装・試験する。

**完了条件:** 通常待機・Voice Editor録音・チューナーの切替と競合を自動試験し、実機でマイクと関連プロセスの解放を直接確認する。旧方式への復帰手順を確認してから移行する。

## 共通の進め方と未決事項

- 各段階の実装・自動試験・実機確認は区別して記録する。第2段階は一操作の移行条件を満たしたら、残る汎用基盤の整備と並行して第3段階へ進む。各段階の未完了事項と完了条件は維持する。
- 横断インターフェース、許可先、マイク制御や共通検証条件を変更する場合は、[横断管理台帳](cross-repo-ledger.md)と該当契約を同じ変更単位で更新する。
- 管理層の実行形態、表示できないページでの継続方式、拡張間通信の実現可能性を決める。JSONの正確な形式、語彙、候補選択の時間や通知方法は設計・検証により定める。
- 既存のTHE SESSION TOOLSとVoice Editorを維持し、管理層が使えないときの切替・復旧手順を確保する。
